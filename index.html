Microsoft Teams — Protocol Handler Abuse via Disguised Link

Teams registers 10 URI protocol handlers (sip://, callto://, im://, etc.) that any webpage can invoke. Modern browsers (Chrome/Edge) show an "Allow this site to open Microsoft Teams?" dialog — but the dialog does not reveal what Teams will do (which SIP address will be called, what deep link will open). An attacker disguises the link; the user clicks "Open" thinking it's legitimate; Teams initiates an unsolicited call or action against the target.

Confirmed behavior Browser dialog shown — but content is opaque to user
Attack type Social engineering + protocol handler abuse
Requires Teams installed, one user click on disguised link
Browsers tested Chrome, Edge — all show dialog; Teams launches on "Open"
The Core Issue — What the Dialog Hides
When a page navigates to sip://victim@contoso.com, the browser shows this dialog. The dialog reveals only which app will open — not what it will do. The SIP target, the action being taken, and the fact that a call will be placed are all hidden from the user.

The user clicks "Open" thinking they're opening a Teams meeting link or document. Teams launches and places an outgoing call to the attacker-specified SIP address.

Attack chain
1. Attacker embeds sip://victim@domain as a disguised link on any page
2. User clicks — browser shows "Open Microsoft Teams?"
3. Dialog shows only app name, NOT the SIP target or intended action
4. User clicks Open (habituated to these dialogs, e.g. Zoom/Meet)
5. ms-teams.exe "sip://victim@domain" is invoked
6. Teams initiates outgoing call to victim — no further confirmation
Why this matters
• Browser dialog is opaque — user cannot tell a call is being placed
• Teams call attempt placed to any SIP address without further confirmation
• 10 handlers in HKCU — no admin, no elevation, written at install time
• ldap:// handler: unexpected LDAP queries from Teams process
• Works on all major Windows browsers (Chrome, Edge, Firefox)
