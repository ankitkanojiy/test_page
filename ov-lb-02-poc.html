Okta Verify — FastPass Challenge Injection

App: com.okta.android.auth v9.8.3  |  Server: NanoHTTPD + WolfSSL · localhost:8769  |  Root: challengeHandler → onDeviceChallengeEvent()

Vulnerability
Unauthenticated Challenge Endpoint + CORS Echo
Attack Vector
Network (browser-to-localhost)
Impact
Device signing triggered cross-origin
User Interaction
Required (single page visit)

Attack Chain

1
Victim visits attacker page
Browser loads this page from https://ankitkanojiy.github.io while Okta FastPass is running on the device.
2
Probe: CORS origin echo exploited
GET https://localhost:8769/probe — RequestHandler.addResponse() echoes Origin back as Access-Control-Allow-Origin with no allowlist. Browser permits the read.
3
Device metadata exfiltrated
Response contains publicKeyChain, orgDomain, localDomain, ianaPort. Attacker now knows the enrolled org and can craft a valid challenge.
4
Challenge injected
POST https://localhost:8769/challenge with attacker-controlled JWS. challengeHandler calls AuthenticatorBindingManager.onDeviceChallengeEvent(SIGNED_NONCE, LOOPBACK) — no HTTP auth check.
5
Device signing triggered
If UserMediationChallenge resolves to NONE (no-interaction enrollment), the device signs the nonce silently — MFA bypassed.

Proof of Concept Checks

Note on TLS: The FastPass loopback server uses WolfSSL with a device-bound certificate. On an enrolled device, Okta installs a trusted CA cert for the loopback domain — the browser will trust it. On an unenrolled device, the fetch will fail with a TLS/CORS error (expected). The PoC logs the exact failure so you can verify the endpoint exists regardless.

Root Cause — Decompiled Code

File: com/okta/devices/loopback/service/RequestHandler.java (OV-LB-01 root)

httpResponse.addHeader("Access-Control-Allow-Origin",
  CollectionsKt.firstOrNull(request.getHeaders().get("Origin")));

Every origin is reflected — no allowlist, no validation. Access-Control-Allow-Private-Network: true also returned unconditionally.
File: com/okta/devices/loopback/service/RequestHandlerKt.java (OV-LB-02 root)

AuthenticatorBindingManager.INSTANCE.onDeviceChallengeEvent(
  new DeviceChallengeEvent(orgId, challengeJws, MethodType.SIGNED_NONCE,
    LoopbackBinding.INSTANCE.getBindingId(), keyId, 0L, BindingType.LOOPBACK, ...)
);

No HTTP authentication, no origin check, no CSRF token — called directly from the loopback request handler.

Recommended Fix

1. CORS allowlist: Replace origin echo in addResponse() with a strict allowlist of Okta-owned origins.
2. Challenge authentication: Require a server-issued nonce/token in challengeHandler before dispatching the event.
3. Remove PNA header: Do not emit Access-Control-Allow-Private-Network: true unless the requesting origin is explicitly allowlisted.
